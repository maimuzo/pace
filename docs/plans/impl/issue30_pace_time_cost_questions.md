# PACE を短い時間と少ない費用で回し、本当に人間が決めるものだけを訊く（#30 の計画）

**言いたいこと。**PACE は、AI とスクリプトだけで、全ての決定に根拠を持つプランを作り上げる。人間への質問は必要最小限にする。
この計画では、まず PACE が求めるものと避けるものを決め、それに照らして PACE を動かすモデルを選び、そのあと時間・費用・質問を減らす作りに直す。

- この文書は、#30 のコメントに分かれていた計画（2026-10-20 の1版と2版）と、その後オーナーと決めたことを1本にまとめたものである。食い違ったらこの文書が正である。
- 文どうしの食い違いと、ファイルが実在するかの確認は、PACE に入れる前に、PACE とは別に回す Opus 5.5 で済ませておく。PACE の仕事には入れない（オーナーの指示）。

## 1. なぜやるか

**言いたいこと。**いちばん単純なプランでも時間と費用がかかりすぎ、質問も多すぎて、使われない。

- #9 で、PACE を6本のプランに当てた。いちばん単純な issue224（137行）でも、3周で63分・$42.9 かかり、最後の周に質問が21件出た。いちばん長い issue134（1,081行）では6時間3分・$343.6 かかった。
- issue224 の質問21件を、プラン・設計文書・コード・issue の議論と照らすと、本当に人間が決めるものは1件だけだった。
- 書き手が直すもの（fixes）は、6本のうち5本で、周を重ねても減らなかった。
- 人間は細かい質問に答えたくないし、根拠を作るのに手間を掛けたくない（オーナーの言葉）。

## 2. PACE が求めるもの

**言いたいこと。**目的は、AI が理由を持たずに決めた決定を外から見つけて詰め、すべての決定が根拠を持つプランにすることである。

1. 決定を全部取り出し、決定ごとに、プランのどの文からどう推論したかのグラフを作る。選ばなかった別案を退ける理由も含む。根拠に使う文は、プランに実在する原文に限る。
2. グラフを1つにつなぎ、循環論法・根拠切れ・プランに無い前提への依存を、スクリプトで機械的に見つける。
3. 根拠を敵対的に疑って反論を出し、弱い枝を刈る。原則と逆向きの決定や、価値判断を黙って決めている決定も見つける。
4. AI が直せるものは AI がプランを直す。足りない事実は、AI がコードや文書を調べて書き足す。
5. 価値判断だけを人間に訊く。プラン・issue の議論（人間の発言）・会話の記録・設計文書・コードで答えや方向が出ているもの、自明なものは訊かない。質問は、止めている決定の数が多い順に並べる。回答は新しい前提になる。
6. 根拠のグラフは毎回作り直し、反論が出なくなるまで直して回して収束させる。同じプランなら同じ結果になる。
7. 判断は人間がするが、人間はファイルを書かない。プランは自然文のままで、印や構造化の書式を埋め込まない。
8. どのプランでも、使われなくならない程度の時間と費用で、根拠のあるプランまで回りきる。スクリプトで済む処理はスクリプトに任せ、AI の使い方も無駄を省く。数万件の規模でも処理できる。
9. continuo が issue の作業計画を書いたら、人間に承認を求める前に、その計画へ自動で PACE を当てられる。

出どころは docs/idea.md の0〜2章・8章・10〜12章と、docs/plans/pace_design.md の11節である。全27項目の一覧は #30 のコメント（2026-10-26）にある。

## 3. PACE が避けるもの

**言いたいこと。**大前提が崩れる形は6つある。評価は、この6つが起きていないかを測る。

| 避けるもの | 何が起きるか |
| --- | --- |
| 1. 人間に訊かなくてよいことを訊く | 訊いてよいのは、プラン・issue の議論（人間の発言）・会話の記録・設計文書・コードのどこにも答えが無く、AI が調べても決まらない価値判断だけである。AI が自分で考えた別案を退ける理由・答えの出ていること・コードを読めば分かる事実・同じ論点の言い換え・一度答えた質問・書き手が直せるものを訊くと、確認が面倒になって使われなくなる |
| 2. 人間に、答える以外の手間を掛けさせる | 根拠や評価用のデータを書かせる。読み切れない量を見せる。途中で人の操作が要って止まる |
| 3. 根拠の無い決定を、根拠ありとして通す | 終わったように見えて気づかれないので、いちばん害が大きい。決定の取り出し損ね・支えていない文を根拠につなぐ・循環の見逃し・弱い反論・出どころの無い事実の書き足し・AI の発言を人間の判断として扱う・古い根拠の使い回しで起きる |
| 4. 根拠のあるプランまで行き着かない | 周を重ねても直すものが減らない。回すたびに結果が変わる。長いプランや、ほかの文書を参照するプランで壊れる |
| 5. プランを悪くする | 書き足しでプランが膨らみ、人間が全体を読めなくなる。無難な判断だけが残る |
| 6. 時間と費用がかかりすぎる | 使われなくなるか、回しきれない |

範囲の外: 文どうしの食い違いやファイルの実在の確認、根拠が正しいことの確率的な保証。

## 4. 作業1: モデルを選ぶ

**言いたいこと。**できあがったプランと、そこまでにかかった手間で比べ、精度（根拠の無い決定が残らないことと、訊かなくてよい質問が少ないこと）に問題が無いモデルのうち、いちばん速くて安いものに決める。

これまでに分かったこと:

- issue224 の1周目を、haiku・sonnet・opus（5.5）と gpt-6-luna・gpt-6.1-sol の5モデル × effort（考える深さの設定）medium・xhigh の10通りで回した（#30 のコメント 2026-10-20）。xhigh は、どのモデルでも medium の2.5〜4倍の時間がかかり、質問も増えた。
- 人間への質問の約95%は、モデルではなく、分類の AI が自分で考えた別案から出ていた。
- いちばん重い設定（opus・xhigh）との一致や、わざと書き換えた場所への反応では、正しさを測れない。この2つの測り方はやめた。

回し方（オーナーが決めたもの）:

| 項目 | 条件 |
| --- | --- |
| 対象プラン | この文書。回す前に、Opus 5.5 に文どうしの食い違いとファイルの実在を確かめさせ、問題が挙がらなくなるまで直す。直した箇所はオーナーに見せる |
| モデル | haiku・sonnet・opus（5.5）と gpt-6-luna・gpt-6.1-sol。effort はすべて medium |
| 回し方 | Claude の3つは pane の Claude Code から、Codex の2つはスクリプトから `codex exec` で回す。`claude -p` は使わない |
| 段階1 | 1周目だけを回し、書き手はプランを直さない。終わったら止めて、オーナーが決定のグラフを見て、使い物になりそうかを決める |
| 段階2 | オーナーが続けてよいと決めたときだけ進める。最大3周。書き手は、実際の使い方と同じ Opus 5.5・medium にそろえる（Codex の2つでも、プランを直すのは pane の Opus 5.5） |
| 質問への回答 | 周ごとに、5モデルの質問を1つの一覧にまとめる。同じ決定の同じ論点への質問は1つにする。オーナーは一覧にまとめて答え、書き手が回答をそれぞれのプランへ書いてから次の周へ進む |
| 周ごとのまとめ | 書き手がプランのどこをどう直したか（差分）。根拠の無い決定（状態が根拠なし・前提が足りない・循環のどれか）のうち、根拠ありになったもの・変わらないもの・新しく出たもの。直すものと質問の数の変わり方。これを見て、オーナーが何周回すかを決める |

測るもの:

| 避けるもの | 何を数えるか | 誰が数えるか |
| --- | --- | --- |
| 1 | 最後に残った質問のうち、訊かなくてよかった数。答えになる原文がプラン・issue の議論（人間の発言）・会話の記録・設計文書・コードにあるもの（引用の実在はスクリプトが確かめる）と、AI が考えた別案から出たもの | 判定役の AI とスクリプト |
| 2 | 人の操作が無いと進めなかった回数。人間に見せる show.md の行数 | スクリプト |
| 3 | 最後のプランに残った根拠の無い決定（状態が根拠なし・前提が足りない・循環のどれか）の数。ただし、足りない前提が人間への質問になっていて、回答を待っている決定は除く。書き手が書き足した事実のうち、出どころが無いか、出どころが実在しないものの数 | 判定役の AI とスクリプト |
| 4 | 止まるまでの周の数と、周ごとの直すものの数 | スクリプト |
| 5 | 最後のプランの行数の増え方 | スクリプト |
| 6 | 止まるまでの時間と金額（書き手と判定役の分を含む） | スクリプト |

- 判定役の AI は1つにする。
- 決め方: 3 の数が、いちばん少ないモデルとの差2件以内で、4 で直すものが周ごとに減ったモデルを残す。段階2へ進まなかったときは、段階1の結果で 3 を数え、4 は見ない。残ったモデルのうち、1 の数がいちばん少ないモデルとの差2件以内のものを残し、その中でいちばん速くて安いものに決める。2件の線は仮の値で、測ってから見直す。
- 人間が採点する場面は無い。オーナーが見るのは、回す前に直した箇所と、段階1のあとのグラフ（下の見せ方の見本）と、周ごとのまとめと、質問の一覧だけである。
- 費用の見込みは、段階1で約 $45（issue224 の1周目の額から見積もった。測っていない）。

決定のグラフの見せ方:

- 決定が50件を超えると、決定ごとの根拠の木を並べ続ける形は読めない。大きな論証を読み進めることが実務者の最大の悩みだという調査（arXiv:1803.08097）があり、NASA の AdvoCATE や Assurance 2.0 のツールも、問題のある所だけを先に出し、全体は畳んで見せている。
- 1枚目は、人間が確かめるべき決定だけの一覧にする。未解決の反論・足りない前提・人間への質問がある決定を、止めている決定の数が多い順に並べ、片付いた決定は件数だけ出す。
- 2枚目は、全決定を1決定1行の表にする。列は、決定の原文と行・根拠にしたプランの文（行つき）・選ばなかった別案と退けた理由・足りない前提・反論（処理済みの数／全体の数）・質問・状態（根拠あり・前提が足りない・根拠なし・循環）。NASA の表形式の書き方（NASA/TM-2017-219650）に倣う。
- 根拠の木は、表の行を選んだときだけ、その決定の周りを開く。プランの本文からも、各文がどの決定の根拠になったかを引けるようにし、どの決定にも使われない文と、根拠の見つからない決定を色で分ける。
- ファイルの中では1枚目と2枚目を Markdown の表で出す。実際の運用では、4つを1つのページにまとめ、状態で絞り込み、質問にその場で答えられるようにする。2周目からは、前の周から変わった決定だけを見せる。
- いまの report.md は決定の ID と状態しか出さず、人間には読めない。段階1では、ファイルの中の形と1つのページの見本を両方作り、オーナーに見せる。

## 5. 作業2: 時間・費用・質問を減らす5つの直し

**言いたいこと。**作業1で選んだモデルで、次の5つを PACE に入れ、issue224 と、この文書で測り直す。

| 直し | 中身 | 効く先 |
| --- | --- | --- |
| ジョブをスクリプトで配る | AI に頼む仕事（ジョブ）を、書き手の会話を通さず、スクリプトが選んだモデルへ直に配る。書き手は周の終わりに fixes の要約を読んでプランを直すだけにする | 書き手の会話が膨らむ費用（issue224 の3周で $16.5、そのうち67%が読み直し） |
| 根拠付けの記憶の鍵を絞る | 鍵を「決定の文と、その決定が選んだ前提の文」に絞り、プランのほかの文が変わっても前の答えを使えるようにする | 2周目以降の根拠付け（いまは毎周すべてやり直している） |
| 別案を、プランに書いてあるものだけにする | 分類の AI が自分で考えた別案からは、人間への質問を作らない | 質問の約95% |
| 質問の前に、答えが既にあるかを照らす | プラン・issue の議論（人間の発言）・会話の記録・設計文書・コードを材料に、答えがあるものは出どころ付きで fixes に回す。同じ決定の同じ論点への質問は1つにまとめる | 答えの出ている質問 |
| 周の止め方 | fixes が前の周より減らなければ止める | 周を回すほど fixes と質問が増える動き |

直すファイルは `plugins/pace/scripts/pace.py`（と、配るスクリプトの新しいファイル）、`plugins/pace/skills/pace/SKILL.md`、`plugins/pace/agents/*.md`、`tests/`、`docs/plans/pace_design.md`・`pace_design_slim.md`・`README.md` である。
