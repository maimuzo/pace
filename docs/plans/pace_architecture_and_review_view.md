# PACE の構成と、決定根拠グラフを人間がレビューする見せ方の検討

**言いたいこと。**PACE の時間は、ほとんどが AI のジョブ（subagent）で、グラフの計算（pace.py）は 0.4〜1.8% しかない。だから、グラフを Go の常駐プロセスのメモリに持っても、全体はほとんど速くならない。効くのは、ジョブの数と遅いジョブを減らすことと、波ごとに全部の束を待つのをやめることである。見せ方は、人間の発言を地面に置き、決定を高さ方向に積む「鉄骨の3D 表示」をブラウザ（TypeScript と three.js）で試作し、同じ操作の2D 表示と比べて決める。

- オーナーの問い（2026-10-28 の #30 のチャット）: 「決定根拠グラフについて、ファイルに書き出すことに意味はあるか? たとえばgo langで実装し…go routineなどを使って、構成要素の更新を行うたびにグラフ全体の検査を平行に行うようにすれば、グラフの完成までの時間を短縮できる?」「3D空間上に基礎となる人間の発言があり、そこから柱や梁となる設計内容が伸びていく様を、3D上のグラフ構造として表現し…」
- 実測の元: #30 の計画ファイルの写しを effort medium で1周目だけ回した本番の記録（2026-10-28。~/pace-eval/transcripts/issue30-cmp-<モデル>-medium/）。数えたスクリプトは 2章の終わりに置く。

## 1. 決めたこと

| 問い | 決めたこと |
| --- | --- |
| グラフを Go の常駐プロセスのメモリに持てば速くなるか | ならない。削れるのは、多くても全体の約3%（2章） |
| 更新のたびにグラフ全体を並列に検査すれば、完成が早まるか | 検査そのものは速くならない。ただし「波を待たずに、終わった束から次のジョブを配る」形にすれば、opus で約50分（全体の約21%）縮む見込みがある。これは言語を変えなくても pace.py でできる（3章） |
| ファイルに書き出す意味はあるか | ある。止まっても続きから回せること、人間と別の道具が同じものを読めること、計測で使ったことが理由（3章） |
| 見せ方 | 人間の発言を地面に置き、決定を、土台からの段数の高さに積む3D 表示（4章） |
| 作る環境 | ブラウザ。言語は TypeScript、描画は three.js、最初の試作は 3d-force-graph（5章） |

## 2. 時間がどこで使われているか（実測）

**言いたいこと。**3モデルとも、時間の 74〜90% は subagent が働いている時間、10〜25% は書き手（Opus）の手番、pace.py は 0.4〜1.8% だった。subagent の時間の 7〜8割は根拠付け（link）の段である。

| モデル | 全体 | subagent が働いていた時間 | 書き手だけの時間 / pace.py の時間 |
| --- | --- | --- | --- |
| claude-opus-5-5 | 236.5分 | 206.1分（87.2%） | 26.1分（11.0%） / 4.3分（1.8%） |
| claude-sonnet-5-5 | 65.9分 | 48.7分（73.8%） | 16.5分（25.0%） / 0.8分（1.2%） |
| claude-haiku-5-5 | 137.6分 | 123.3分（89.6%） | 13.8分（10.0%） / 0.6分（0.4%） |

- pace.py の next は、opus で83回打ち、合わせて4.2分、いちばん長い1回で6.4秒だった。グラフの検査（輪の検出・状態の伝わり）は、この中に入っている。
- subagent の中でファイルを読み書きした待ち（Read と Write の道具の時間）は、opus で全部の束を足して9.1分だった。並列の平均は約2.25本なので、全体の時間に効くのは4分ほどである。

opus の subagent の時間を、段ごとに分けたもの（全部の束の時間の和。並べた分も足している）:

| 段 | 束 / ジョブ | 時間の和（割合） | 1ジョブあたり |
| --- | --- | --- | --- |
| 根拠付け（link） | 243 / 1241 | 327.9分（70.7%） | 15.9秒 |
| 輪を断つ（decycle） | 14 / 22 | 97.1分（20.9%） | 264.9秒（いちばん長い束は31分） |
| 反論（review） | 18 / 50 | 21.5分（4.6%） | 25.8秒 |
| 分類（classify）と裁定（adjudicate） | 12 / 85 | 17.5分（3.8%） | 6〜28秒 |

- 波（同じ時期に出した束の組）ごとに、いちばん遅い束を待っている。opus は波の長さの合計が206.1分で、束を4本に平らにならせたときの下限の目安が155.8分なので、約50分を遅い束の待ちに使った（sonnet は約10分、haiku は約23分）。
- haiku も、輪を断つ段が1ジョブ316秒と遅い。haiku の輪を断つ subagent は、「全部の辺を1つの順序に並べ、その順序に逆らう辺を切れば必ず輪が消える」と提案していた（輪を断つ段を、決まった手順で解ける余地がある）。
- 数えたスクリプト: 時間の内訳は `timeline.py`、段ごとの内訳と波の待ちは `stages.py`。どちらも `python3 -I <スクリプト> ~/pace-eval/transcripts/issue30-cmp-<モデル>-medium` で動く。置き場は #30 の計測の道具と同じ ~/pace-eval/analysis/。

## 3. Go の常駐プロセス案の評価

**言いたいこと。**常駐プロセスで速くなるのは pace.py とファイルの読み書きの分だけで、合わせて全体の約3%である。速さが欲しいなら、次の3つが効く。どれも言語を変えずにできる。

| 効く直し | 縮む見込み（opus） | なぜ効くか |
| --- | --- | --- |
| 波を待たず、終わった束から次のジョブを配る | 約50分（約21%） | いまは波の中のいちばん遅い束を全員が待つ。依存の無いジョブは、前の波の終わりを待たなくてよい |
| 輪を断つ段を、決まった手順（辺を1つの順序に並べ、逆らう辺を切る）で解き、AI には切る辺の候補から選ぶことだけを頼む | 輪を断つ段の97.1分（束の時間の和）の多く | AI が輪そのものを探して何度も読み直すのに、1ジョブ265秒かかっている |
| 根拠付けのジョブの数を減らす（同じ単位の決定をまとめて1ジョブにする・cache を当てる） | 根拠付けの327.9分（束の時間の和）に比例して縮む | 時間の7割がこの段で、1ジョブ16秒の積み重ねだから |

- 「更新のたびにグラフ全体を並列に検査する」は、検査が1回数秒なので、並べても縮むのは数秒である。効くのは、検査の結果を使って「いま配れるジョブ」を早く見つけ、待たずに配ることのほうである。それは上の1行目と同じ直しになる。
- 波を待たない形にすると、書き手（Opus）が束の終わりの知らせのたびに起きて next を打つので、書き手の手番（いま11〜25%）が増えうる。試すときは書き手の時間も一緒に測る。
- 上の3つは、#30 の計画の「時間・費用・質問を減らす5つの直し」（[docs/plans/impl/issue30_pace_time_cost_questions.md](impl/issue30_pace_time_cost_questions.md) の5章）と重なる。入れるかどうかは、そちらで決める。

**ファイルに書き出す意味。**次の3つがあるので、書き出しはやめない。

- 止まっても続きから回せる。2026-10-28 の本番では、セッションが閉じて計測のプロセスが止められても、`.pace/` の pending.json と答えのファイルから続きを回せた。
- 人間と別の道具が同じものを読める。グラフのページ・採点役・計測の道具は、どれも `.pace/` を読む。
- メモリだけに持つと、常駐プロセスが落ちたときにグラフを失う。それを避けるには結局ファイルへの書き出しが要る。

**採らなかった案。**pace.py を Go の常駐プロセスに書き換え、ソケットで更新を受ける案は採らない。削れるのが約3%で、常駐プロセスの起動・停止・落ちたときの扱いという新しい壊れ方を増やすから。

## 4. 見せ方: 鉄骨の3D 表示

**言いたいこと。**決定根拠グラフは木ではなく、土台が複数ある有向グラフである。土台（人間の発言・文書・コードの事実）を地面に置き、決定を、土台から何段離れているかの高さに積む。人間が選んだ1つの決定から、土台の方向と、派生する方向へ、キーで辿れるようにする。

- 大きさの目安: opus の1周目で、決定311件・前提169件・反論143件、輪を断つ段で外した辺662件。点が数百〜千、辺が数千の規模で、ブラウザで十分に描ける。

| 置き方・描き方 | 中身 |
| --- | --- |
| 高さ | 土台（人間の発言など）は地面（高さ0）。決定は、土台からの最長の段数の高さに置く。高さは固定し、横の位置だけを力の計算で決める |
| 横の位置 | プランの節ごとに、地面の上で寄せる。同じ節を支える土台と決定が、近くに立つ |
| 柱と梁 | 同じ節の中の支えの辺は「柱」（縦に近い太い線）。節をまたぐ支えの辺は「梁」（細い線） |
| 色と太さ | 状態で色を分ける（根拠ありは緑、前提が足りないは黄、根拠なしは赤）。点の大きさは、その決定に頼っている決定の数。1つの土台だけに頼っている決定は、印を付けて弱い所として目立たせる |

| 操作 | 何が起きるか |
| --- | --- |
| 決定をクリックするか、検索で選ぶ | その決定に寄るようにカメラが動く。その決定の祖先（土台までの支え）と子孫だけを残し、ほかを薄くする |
| ↓キー / ↑キー | 支えの1段下（土台の方向）/ 派生の1段上へ、カメラが動いて移る。行き先が複数あれば、←→で選ぶ |
| Enter | 横の欄に、その決定の文・プランの行・支えの原文・足りない前提・質問を出す（読む中身は文なので、3D の中には書かない） |
| 土台までの道を見る | 選んだ決定から土台までの道を光らせ、道に沿ってカメラが動く |

**なぜこの見せ方か。**オーナーが確かめたいのは「この決定がどの発言に支えられているか」と「どこが弱いか」である。高さを土台からの段数に固定すると、上下が「支え ↔ 派生」の向きに一致するので、↑と↓のキーだけで辿れる。3D のグラフは、動かしながら見ると、2D よりも大きなグラフで道を辿りやすい、という実験の報告がある（Ware と Franck、1996 年など）。

**弱い所と、その確かめ方。**3D は、手前の点が奥を隠すことと、どこを見ているかを見失うことが弱い。そこで、同じ置き方を2D に倒した表示（土台を下の行に並べ、高さを行にした層の図）も、同じ操作で作る。オーナーに、両方で「この決定を支える人間の発言はどれか」を何問か答えてもらい、かかった時間と迷った回数で選ぶ。

**採らなかった案。**

| 案 | 採らない理由 |
| --- | --- |
| 木（1つの根から枝分かれ）の図 | 土台が複数あり、1つの決定が複数の土台に支えられるので、木にすると同じ決定が何度も出る |
| 力の計算だけで3D に散らす図 | 上下に意味が無く、どちらが土台か分からない。「鉄骨」の形にならない |
| 保証ケースの図の書き方（GSN など）をそのまま使う | 1つの主張を上から分けていく木の書き方で、土台が複数ある形に合わない。部品（主張・根拠・前提を形で分けること）は借りる |

## 5. 作る環境と言語

**言いたいこと。**ブラウザで作る。PACE はいまも1つの HTML ファイル（graph.html）を書き出しているので、同じ形のまま、入れる物も要らない。言語は TypeScript、描画は three.js で、最初の試作には 3d-force-graph を使う。

| 環境 | 良い所 | 悪い所 | 判断 |
| --- | --- | --- | --- |
| ブラウザ（WebGL、TypeScript、three.js） | 入れる物が無い。1つの HTML ファイルで渡せる。点が千個の規模なら十分に速い。3D のグラフの部品が多い | 大きな UI を作るなら、組み立てに手間がかかる | 採る |
| WebAssembly（Rust と Bevy・egui など） | 点が数万を超えても速い | この規模では速さが要らない。作るのと直すのに時間がかかる | 採らない（点が数万を超えたら考え直す） |
| OS のネイティブのアプリ（Godot・Unity など） | 3D の操作は作りやすい | 入れて配る手間がある。PACE の出力から開く流れが遠い | 採らない |
| TUI | ターミナルの中で完結する | 3D は描けない | 3D の代わりにはしない。文で「土台の方向・派生の方向」に辿る道具としては、後で足す余地がある |

- 部品: 3d-force-graph（three.js の上で、力の計算・点のクリック・カメラの移動を持つ。点の高さを固定する指定ができる）。UI が大きくなったら、React と react-three-fiber に移す。
- データの渡し方: pace.py（または viz/render.py）が、点・辺・高さ・節を JSON にして HTML に埋め込む。グラフの計算は Python に置いたままにし、ブラウザは描くだけにする。

```json
{"nodes": [{"id": "D_dab50efc_1", "kind": "decision", "status": "needs_gap", "height": 3, "sec": "4.1",
            "line": 65, "text": "…", "dependents": 12, "single_foundation": false}],
 "edges": [{"from": "H_owner_6441498532", "to": "D_dab50efc_1", "type": "column"}]}
```

- 版は、作るときにその時点のものを確かめて固定する（この文書を書いた時点では確かめていない）。
