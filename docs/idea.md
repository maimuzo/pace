# PACE — 基本構想

**PACE: Pathway Autonomous Construction Engine.**
A framework for autonomous construction and validation of logical decision graphs in AI agents.

（日本語の説明：AI エージェントが書いた設計プランについて、決定の根拠をつなぐ論理的な決定グラフを自律的に組み立て、検証するフレームワーク。設計プランの決定根拠を外から詰める仕組み。）

> **この文書の読み手**
> OSS プロジェクト **PACE** に関わる AI と人間。
> 2026-10-14〜15 に、オーナー（まいむぞう）と Claude が行った検討と実験を、結論・却下した案・数値・失敗の記録まで含めて残したもの。
> **確定した方針**（オーナーが明言したもの）と、**Claude の提案・実験結果**（変えてよいもの）を区別して書く。迷ったら「1. 課題」と「2. 確定した方針」を優先すること。

---

## 0. 一言でいうと

AI（Claude Code など）が書いた**設計プランファイル**を入力にして、

1. プランの中の**決定**をすべて取り出し、
2. 決定ごとに「プランのどの前提から、どういう推論でそう決めたのか」という**根拠のグラフ**を作り、
3. **スクリプト**が、循環論法・根拠切れ・プランに無い前提への依存を機械的に検出し、
4. **AI**が、根拠を敵対的に疑って反論を出し、
5. 直せるものは AI がプランを直し、価値判断は**人間に質問**し、
6. 根拠グラフを**毎回ゼロから作り直して**、反論が出なくなるまでくり返す。

最後に残るのは「**その時点の条件で、このプランがベストである**と、全決定について根拠付きで示されたプラン」である。

## 1. 課題（なぜ作るのか）

### 1.1 オーナーの問題意識

- AI と会話して設計していると、**AI が決定理由を持たずに仕様を決めていることが多すぎる**。
- AI がこれを自分で改めることは不可能。だから**外部から決定根拠を疑い、詰める仕組み**が要る。
- 狙いは「AI 自体が、すべての決定について理論的になる」こと。すべての決定が根拠を持ったプランにする。

### 1.2 具体例（実在のプランから見つかった問題）

実験対象は `maimuzo/continuo` の `docs/plans/impl/issue224_config_reload.md`（137行・96単位、continuo を止めずに `WORKFLOW.md` を読み直す機能のプラン）。このプランを仕組みに通すと、次のような問題が出た。

- **理由が書かれていない決定**：「読み直しは `Tick` の頭で1回だけ行う」。ファイル監視・SIGHUP（シグナルで読み直す方式）・別のタイマーではなく巡回の中で行う理由が、プランに無い。
- **循環論法**：3つの決定が互いを理由にしていた。
  - 「失敗しても既存の状態を触らない」の理由 → 「外部プロセスを起こさない」
  - 「外部プロセスを起こさない」の理由 → 「失敗したら古いまま続ける」
  - 「失敗したら古いまま続ける」の理由 → 「失敗しても既存の状態を触らない」
  - 各決定を別々に見ているときは気づけず、**グラフを1つに結合して初めて検出された**。
- **原則の向きが逆になっている**：5節で「書き漏らしは安全側（変わらない側）へ倒す」と原則を立てている。ところが6節では、値を伏せるキーとして `claude.env` の1つだけを指定している。後から鍵を入れうるキーを足した人が伏せる指定を書き漏らすと、**値がログに出る側に倒れる**。
- **人間の価値判断を黙って決めている**：「4キーを混ぜた結果が検査に落ちたら、4キー全部を古いままにする」。通るキーだけ採用する案もあり、どちらを取るかは安全性と反映度のどちらを重視するかで変わる。

### 1.3 規模

- 137行のプランから決定が50〜72件出た（1単位あたり約0.5件）。
- continuo の全体設計 `continuo_design.md` は約18,000行・13,197単位（約1.5MB）。同じ比率なら決定は数千〜1万件、根拠ノードまで含めると**数万件**になる。ただしこの比率は1本のプランから出した値で、ほかのプランで成り立つかは未確認（10章）。
- **すべてを AI に任せると、時間もコストも安定性も足りない**（オーナーの指摘）。AI に頼る部分と、スクリプトで機械的にやる部分を分ける必要がある。

## 2. 確定した方針（オーナーが明言したもの）

### 2.1 対象と目標

| # | 方針 | 補足 |
|---|---|---|
| P1 | 根拠グラフを適用するのは**プランファイルだけ**。コードには適用しない | 「プランファイルが根拠をもって作られれば、コードはそんなにブレない」 |
| P2 | 大元（正）は**プランファイル**。人間が全体像を理解できることと、良い設計にすることが大前提 | YAML だけでは人間が全体像を理解できない |
| P3 | プランファイルは**自然文で自由に書く**。マーカー・マークアップは埋め込まない | 「お前（AI）はそんなに賢くない。絶対に更新されなくて破綻する」 |
| P4 | 設計がある程度固まった段階で、**すべての決定根拠を書き出して**、理由が正当か確認する | |
| P5 | 根拠ファイルは**使い回さず、毎回すべて新しく作り直す** | 更新漏れの防止 |
| P6 | 目標は「**その時点の条件でプランがベストであることを示す**」こと。反論する必要がない状態までループしながら修正すれば到達できる | 条件が変わっても変更不要にする、という意味ではない |
| P7 | 「すべての事柄をより細かく理由付けする」ことで、決定を理論武装する | 根拠は1プランあたり数万件規模を想定。効率的に処理する仕組みが必要 |
| P8 | 根拠が**正しいことの保証**（確率的な精度保証など）は**後の段階**。今の目標は「すべての決定が根拠を持つ」こと | 「その時初めて確率の話が出てくる。今はそこまで達してない」 |
| P9 | AI 依存の部分と、スクリプトで機械的に行う部分を**分ける** | 時間・コスト・安定性のため |

| H2 | 価値判断（何を重視するか）で決まる事柄は、**AI が人間に質問して決めてもらう**。それも含めて設計ができあがっていくのが普通 |
| H3 | 人間の発言を根拠の根っこにしたい場合、**Claude Code のセッション JSONL を見れば人間の発言は判別できる**（後の段階の話。現段階はプランファイルだけで閉じる） |

| # | 方針 |

| S2 | ただし最初の実験では、複雑になりすぎるので**プランファイルだけ**に絞った。これは「今の段階では省く」という判断であって、スコープから外したのではない |

- 議論の初期（マーカー方式など）は「決定ではなく参考」として扱う、と途中で明言された（→ 4章）。
- 「どこでループを動かすか（フックか専用コマンドか）」のような細部は、**実装段階で決めればよい**。

### 2.5 進め方

| # | 方針 |
|---|---|

| W2 | 今の段階は**机上の空論**で、どれぐらい効果があるかは未知数。**一旦実装して、実際の設計作業で使ってみる**。効果を測ってから、作り込む部分を決める（12章） |

### 2.6 実行環境の制約

- `maimuzo/continuo` の CLAUDE.md に「`claude -p` は使用禁止（従量課金になるため）。Claude Agent SDK と Anthropic API の直叩きも同じ理由で対象外」とある。
- そのため実験では、**AI の処理はすべて、固定料金で動く Claude Code セッションのサブエージェント**に任せた。スクリプトは AI を直接呼ばない（→ 6章）。
- 新プロジェクトでも、AI の実行手段を**差し替え可能**にしておくこと（サブエージェント、API、他社モデルなど）。

## 3. 用語

具体例は、すべて issue224 のプランから取った。

| 用語 | 意味 | 例 |
|---|---|---|
| **単位（unit）** | プランを機械的に切った最小の断片。文・箇条書きの1項目・表の1行・見出し | 「`Orchestrator` が持つ設定（`cfg`）そのものは差し替えない。」 |
| **決定（decision）** | プランが何かを選んでいて、要求を満たす**別の選び方**があり、選び方によって**振る舞いや作り方が変わる**もの | 「`cfg` は差し替えない」（別案：「`cfg` 全体を錠付きで差し替える」） |
| **別案（alternatives）** | その決定で選ばなかった現実的な選択肢。根拠は別案を退ける理由まで含む | 「`reflect.DeepEqual` で丸ごと比べる」 |
| **前提（premise）** | 決定ではない記述。根拠の葉になる。次の3種類 | |
| └ fact（事実） | 現状についての記述 | 「本体は `reflect` を1度も使っていない」 |
| └ requirement（要求） | 満たすべき要求・目標 | 「止めずに設定を読み直したい」 |
| └ value（価値判断） | 何を重視するか | 「半端に効く仕組みより安全側に倒す」 |
| **中間主張（claim）** | 前提と決定の間に挟む推論の途中の主張。プランに書かれていなくてよい | 「1台ならプロセス内の値は全リクエストで共有される」 |
| **gap** | 根拠を通すのに必要だが、**プランに書かれていない前提**。根っこにはならない | 「シグナル（SIGHUP）で読み直す案を退ける理由が、プランに無い」 |
| **step（推論の1段）** | 「from（前提・主張の集合）から to（主張・決定）が導ける」という1段。warrant（なぜ導けるか）を必ず書く | |
| **反論（defeater）** | 決定や推論を崩しうる疑い。Assurance 2.0 の用語。種類は logic / missing / fact / value | 「4キーを写すだけで正しい設定ができあがることを暗黙の前提にしている」 |
| **反論の処理** | refuted（プランの前提で反証できた）／ accepted（反論が正しい。プランの修正が要る）／ needs_human（人間の価値判断が要る） | |
| **根に届く（rooted）** | 決定から step をたどると、すべての枝がプランの前提で終わること | |
| **gap 待ち（needs_gap）** | どこかの枝が gap で終わっていること | |
| **根拠なし（ungrounded）** | step が無い、または循環の中でしか支えられていないこと | |
| **自前の推論が完結（locally complete）** | ほかの決定を「別に審査されるもの」として前提扱いしたとき、自分の推論に gap が無いこと | |
| **gap の効き（leverage）** | その gap が埋まれば根に届くようになる決定の数。依存を推移的にたどって数える | 「再起動は許容できない、という基準」の gap が34件の決定を止めていた |
| **ジョブ** | スクリプトが AI に頼む仕事1件分を書き出した JSON ファイル | `jobs/link/D_2e8b33e5_1_r1.json` |
| **実行役（executor）** | ジョブを読んで答えを書く AI（実験では Claude Code のサブエージェント） | |

## 4. 検討の経緯（何を考え、なぜ捨てたか）

この章は、同じ議論をくり返さないための記録である。

### 4.1 最初の案：要求トレーサビリティツール＋人間が書く根っこ（捨てた）

- **案**：仕様・理由・要求を1件1ファイルの YAML にし、`because:` のリンクを持たせる。人間が要求（REQ）を書いて承認し、AI は中間の理由と仕様だけを書く。スクリプトが「すべての仕様が人間承認済みの根に届くか」を検査する。Claude Code のフック（ツール実行の前後に任意のコマンドを走らせる仕組み）で `reqs/` への書き込みを止める。
- **既存ツールの候補**：Doorstop、sphinx-needs、GSN（Goal Structuring Notation。安全性証明で使う記法）。
- **捨てた理由**：人間がファイルを書く前提になっている（H1 に反する）。プランとは別に YAML を持つことになる（P2 に反する）。

### 4.2 既存 OSS の徹底調査（→ 5章に詳細）

結論は「**要件を全部満たす既存のものは無い**」。どれも次のどこかで「強制」が抜けている。
- 理由の無い仕様を**拒否**せず、警告や低い点数で通してしまう。
- 根拠をたどった先が**人間が承認したもの**に行き着くことを保証しない。
- 理由の**作り話**は防げない。

### 4.3 反論（defeater）を書かせる案（考え方は採用）

- **案**：AI に理由と一緒に反論も書かせる。反論を処理するのは人間。
- **狙い**：理由の正しさを評価するのは難しい（もっともらしい説明を読むと納得してしまう）。一方、**具体的な疑いに「はい／いいえ」で答えるのは簡単**。レビューを「説明を読んで納得する」から「疑いに答える」に切り替える。
- **当時挙げた弱点**：
  - AI は自分の判断を守るので、わざと弱い反論（藁人形）を書きがち。対策は反論の種類（前提・代替案・失敗時・コスト）を必須にすること。さらに、**理由を見せずに別のセッションに反論を書かせる**こと。
  - 人間が疲れてすべて「反証済み」で流してしまう。
  - 量が増えすぎる。
  - 反論を処理しても、判断の正しさは証明されない。
- **その後の変化**：反論を処理するのは人間ではなく **AI のループ**にした（4.7）。人間には価値判断だけを聞く（H2）。

### 4.4 YAML を別に持つ案（捨てた）

- **案**：設計根拠を最初から YAML で書かせ、それ自体をプランとして扱う。TSF の「リンク先が変わったら要確認」をフィンガープリント（内容のハッシュ）で実現する。
- **捨てた理由**：オーナーの指摘。プランと YAML が別になると使いづらく、プランから YAML を起こすときに**記載漏れや更新漏れが絶対に起きる**。一方、YAML だけでは人間が全体像を理解できない（P2）。

### 4.5 プランの中に構造化書式で根拠を書く案（捨てた）

- **案**：Markdown のプランに `## DD-007` の見出し、`根拠: [[REQ-012]]` の行、`> 反論 DF-1 [前提] open:` の行を書く。スクリプトが Markdown を直接読む。
- **捨てた理由**：「YAML をそのまま Markdown にしただけで現実的じゃない。AI が実際に書くプランはあんな形ではない」（オーナー）。

### 4.6 自然文のプランを LLM が解析してグラフにする案（採用の起点）

- **案**：プランは自然文で書く。別の LLM が解析してグラフを作り、機械で判定する。エラーがあれば LLM にプランを直させる。オーナーの発案。
- **このとき Claude が付けた条件**：
  - 抽出役の AI には、ノードと辺のすべてに原文の引用を付けさせる。引用がプランに実在するかは、機械が文字列照合で確かめる。
  - 根っこを照合可能なものに限る。
- **このとき Claude が挙げた弱点**：
  - 抽出の見落とし。対策は2回独立に抽出すること。
  - 抽出が毎回揺れる。
  - 引用が実在しても、推論が正しいとは限らない。
  - 計画役が根っこの発言を曲解する。
- **Claude の誤り**：Claude は「機械が保証するのは引用でつながっていることまで。推論の正しさは人間が確認するしかない」とまとめた。オーナーから「**グラフと反論があるなら、それも敵対的に LLM にレビューさせて弱い枝を刈り取り、また根拠付けし、また刈り取る。人間が検討するときの流れをそのまま LLM にやらせればよい**」と指摘された。Claude はこれを受け入れた。

### 4.7 ループの形（採用）

1. **計画役 AI** が、自然文でプランを書く。
2. **抽出役 AI** が、プランから根拠グラフを作る。
3. **機械検証**が、引用の実在、循環が無いこと、すべての決定が根に届くことを確認する。エラーがあれば計画役に差し戻す。
4. **敵対役 AI** が、グラフに反論を出す。
5. 反論の種類ごとに解決する。
   - 論理の問題：判定役の AI が判断する。別のモデルが望ましい。
   - 事実の問題：調査役の AI がコードや文書を読み、引用付きで答える。
   - 実験が要る問題：実行役が計測やテストを走らせる。
   - 価値判断：**人間に質問する**。回答が新しい前提になる。
6. 弱い枝を修正・削除して、2に戻る。
7. 新しい反論が出なくなったら、人間が承認する。

**Claude の誤り**：途中で Claude は「価値判断の反論はどれだけ議論しても答えが出ないので、LLM だけでは完全にならない」と主張した。オーナーの指摘は「**だから人間に質問して決めてもらうんだろう。普通そうだろ。それも含めて設計ができあがっていく**」。人間への質問は、ループの普通の一手である。

Claude が挙げた残りのリスクは2つ。
- 抽出役が、プラン中の判断をノードにし損ねる。
- 書く役と疑う役が、同じ穴を見落とす。

対策は、抽出を2回独立に行うことと、別モデルを混ぜること。もう1つ、LLM 同士で文章だけの議論を回すと、正しくても説明しにくい判断が消え、無難な判断ばかりが残る傾向がある。外部の事実（コード・計測）に当てることで緩和する。

### 4.8 HTML コメントのマーカー案（捨てた）

- **案**：プランの各行に `<!--@D1 ←U2-->` のような HTML コメントを付ける。レンダリングすると見えない。全行にマーカーを必須にして、付け忘れを機械で検出する。
- **捨てた理由**：オーナーの判断で、プランに決定根拠をマークアップするのは現実的ではない。AI が更新し忘れて破綻する（P3）。この時点でオーナーは「ここまでの議論は決定ではなく参考」とした。代わりに採った方式が P4・P5（固まった段階で全部書き出す。毎回作り直す）。

### 4.9 Claude が出して否定された主張（くり返さないこと）

- 「推論の連鎖では誤りが掛け算で効く（1段95%でも10段で約60%）。だから細かくしても強くならない」
  → **否定**。今の狙いは「AI がすべての決定に根拠を持つこと」。確率の話は、根拠の正しさを保証する後の段階で出てくる（P8）。
- 「『変更する必要がない状態』は原理的に作れない」
  → **否定**。条件が変わっても変更不要にする、とは言っていない。**その時点の条件でベスト**であることを示せればよく、それは反論が出なくなるまでループで直せば作れる（P6）。
- 実プランを読まずに抽象論を続けたこと → **否定**。実データで確かめること。

## 6. 方式：AI とスクリプトの分担（実装済みのパイプライン）

> **注意**：この章の設計は、ほぼ issue224 の1本だけを見て作った。分割と候補の規則には、そのプランと continuo の書き方に合わせた部分がある。どこが合わないかは 10章を参照。

実験用の実装は `rg.py`（Python 約1,000行、外部ライブラリ不要）と `EXECUTOR.md`（AI 側の手順書）。`rg` は実験時の仮の名前（rationale graph の略）で、ripgrep のコマンド名 `rg` とぶつかる。PACE では使わない。新プロジェクトでは作り直してよいが、以下の設計判断と、その理由は引き継ぐこと。

### 6.1 原則

1. **スクリプトは AI を呼ばない**。AI に頼む仕事は**ジョブファイル**として書き出すだけ。AI（実行役）がそれを読み、答えの JSON を `*.out.json` に書く。スクリプトは答えを検証して取り込み、次の段のジョブを作る。
   - 理由：AI の実行手段（サブエージェント、API、別モデル）を差し替えられる。従量課金の禁止にも従える。
2. **AI に任せるのは意味の判断だけ**：分類・裁定・根拠付け・輪を断つ・反論（将来はプランの修正も）。それ以外はすべて機械が行う。分割、候補の絞り込み、ID 採番、引用、結合、検証、優先順位、振り分け、周回の制御である。
   - 理由：1周目の実験では、エージェントが作業の相当部分を、自分で Python を書いて機械的にこなしていた。
3. **AI の出力は ID の参照だけ**。引用の文字列や全体の ID はスクリプトが付ける。
   - 理由：引用の捏造が原理的に起きない。1周目では、ID の接頭辞の管理や他の担当の決定の写しに手間を取られ、偽のエラーも出た。
4. **AI に渡す材料の大きさを一定に保つ**。候補を機械で絞るので、プランが巨大になっても、1回の入力はほぼ一定になる。コストは決定の数に比例するだけになる。
5. **内容アドレスのキャッシュ**：鍵は `sha256(段の版 + 段の名前 + 入力 JSON)`。入力が1文字でも変われば鍵が変わるので、**古い結果が使い回されることは仕組み上無い**。P5（毎回作り直す）と、コストの削減を両立する。
6. **独立した2回の判断を機械で比較する**。食い違ったものだけを AI の裁定に回す。
7. **AI の答えは必ず機械で検証する**。駄目なら理由（`previous_errors`）を付けて差し戻す。3回まで。

### 6.2 段の流れ

```
init:  プラン → [機械] 分割 → units.jsonl
next:  ┌[AI]   分類 A（単位の順番どおり）
       ├[AI]   分類 B（単位の順番を逆にして独立に）
       ├[機械] A と B の比較 → 食い違った単位だけ
       ├[AI]   裁定
       ├[機械] ノード化（決定 D_*, 前提 P_*）
       ├ 反復（輪が消えるまで、最大5回）
       │ ├[機械] 候補の絞り込み
       │ ├[AI]   根拠付け 1回目（r1）
       │ ├[機械] AI の need（探してほしい内容）から追加の候補を探す
       │ ├[AI]   根拠付け 2回目（r2。追加があるときだけ）
       │ ├[機械] 決定どうしの辺から輪（強連結成分）を探す
       │ └[AI]   輪を断つ（切る辺を選ぶ）→ 切られた側の候補から外して、もう一度
       ├[機械] 結合・検証（循環、根への到達、gap の効き）
       ├[AI]   反論（自前の推論が完結した決定だけ）
       ├[機械] 反論の検証（refuted の根拠が根に届くか）
       └[機械] レポート
```

使い方：
- `rg.py init <plan.md> <作業ディレクトリ>`
- `rg.py next <作業ディレクトリ>`：結果の取り込みと次のジョブの書き出し。保留中のジョブは `pending.json` に書かれる。
- `rg.py verify <作業ディレクトリ>`
- `rg.py report <作業ディレクトリ>`

運用は「`next` → `pending.json` のジョブを実行役に渡す → `next`」のくり返し。`完了。AI のジョブは残っていない。` が出たら終わり。

### 6.3 各段の詳細

#### 段1 分割（機械）

- Markdown を行ごとに見て、次のように切る。
  - 見出し → `heading`
  - 表の行 → `table_row`（区切り行は捨てる。セルは ` | ` で連結する）
  - 箇条書き → `bullet`
  - それ以外の行 → 「。」で区切って `sentence`
- コードブロックと水平線は捨てる。`**` は除去し、空白を正規化する。
- 単位 ID：`"u" + sha256(見出しの階層 + "\n" + 本文)[:8]`。同じ値が重複したら連番を付ける。
- 各単位の属性：位置 pos、kind、行番号 line、見出しの階層 path、所属する H2 の節 sec、本文 text。
- issue224 のプランは96単位になった。1周目の実験では、決定72件・前提71件の引用が、**すべて単位に対応した**。分割の粒度は十分である。

#### 段2 分類（AI、A/B の2回）

- 節ごとに最大30単位を1ジョブにする。
- 各単位に付けて渡すもの：`section_path` と、前後2単位の本文（`neighbors`。文脈を確かめるため）。
- B は単位の順番を逆にする（順番による偏りを減らす）。
- 出力：単位ごとのラベルの配列。decision（text、alternatives）と premise（ptype、text）。1単位に複数あってよい。
- 検証：入力のすべての uid が、過不足なく1回ずつあること。ラベルの形が正しいこと。
- **キャッシュは単位ごと**。鍵は「段の版 + A/B + 文書名 + 節 + 単位の uid・kind・section_path・text」。**前後の文は鍵に入れない**（6.6 で理由を書く）。

#### 段2b 比較（機械）と 段2c 裁定（AI）

- 単位ごとに、A と B の「決定の数・前提の数」を比べる。一致すれば A を採る。違えば、その単位だけを裁定のジョブにする。
- issue224 では96単位中8単位が食い違った。

#### 段3 候補の絞り込み（機械）

- 決定ごとに、根拠の候補にするノードを次の規則で選ぶ。
  - 同じ H2 の節
  - 前後5単位
  - 冒頭の節（タイトル直下と最初の H2。プランの目標が書かれるため）
  - バッククォートで囲んだ識別子（`` `cfg` `` など）を共有する単位
- 位置の近い順に並べ、最大80ノードまでにする。
- 候補は**単位ごとにまとめて**渡す（`{"plan_text": 原文, "section": 節名, "nodes": [...]}`）。原文を1回だけ載せるためで、入力が平均6,506字から5,775字に減った。
- 1周目のデータで測った結果：
  - 直接の根拠62本のうち49本（79%）を、この規則で拾えた。
  - 漏れた13本のうち12本は、**別の節の決定**を根拠にしていた。
  - ある決定では、86単位中28単位（プランの文字数の35%）に絞れた。
  - 小さいプランでは、候補がほぼ全体を覆う。

#### 段4 根拠付け（AI）

- 入力：
  - `target`：決定。text と alternatives を含む
  - `candidates`：段3で選んだ候補
  - `excluded_note`：輪を断つ段で外された決定。理由に使ってはいけない
  - `previous`：2回目のときの前回の結果
- 出力：`claims`（c1...）、`gaps`（g1...、ptype 付き）、`steps`（from / to / warrant）、`need`（候補に無いが、プランの別の箇所にありそうな前提や決定）。
- 規則（要約。全文は付録A）：
  - 根拠の葉は候補の id だけ。
  - 足りないものは、でっち上げずに gap にする。
  - 別案を退ける理由まで根拠付ける。
  - step は小さく保つ。
- 検証：
  - from が「候補の id ∪ 自分の claims ∪ 自分の gaps」に含まれること
  - to が target か claim であること
  - target に至る step が1本以上あること
  - 自己参照が無いこと
  - **すべての gap が、どれかの step の from で使われていること**
  - warrant が空でないこと

#### 段4a 候補の追加（機械）

- AI が `need` を書いたら、文字の2-gram（隣り合う2文字の組）の出現回数ベクトルのコサイン類似度で、ノードの本文＋単位の原文を検索する。
- need 1件につき最大6件、合計で最大12件を追加し、2回目の根拠付けをする。
- 段3で漏れる「別の節の決定」の受け皿。将来は埋め込み検索（文章を数値の列にして、意味の近さで探す方式）も候補。

#### 段5a 輪を断つ（AI）と反復（機械）

- **なぜ要るか**：決定ごとに独立に根拠付けすると、決定どうしが互いを理由にし合う輪ができる。issue224 では、輪を断つ前は50件中33件が「根拠なし」になり、最大23ノードの強連結成分（互いに行き来できるノードの塊）があった。
- 機械が、決定どうしの辺から強連結成分（Tarjan 法）を探す。成分ごとに、ノードと辺（warrant 付き）をジョブにする。
- AI は各辺について「from が本当に to より先に決まっている理由なのか、並列の決定や帰結にすぎないのか」を判断し、本当の理由ではない辺を最小限切る。
- 検証：切る辺が実在すること。**切った後に輪が残らないこと**（機械が再計算する）。
- 切った辺の from を、to の決定の候補から外し（`excluded_note` を付ける）、根拠付けをやり直す。やり直しで新しい輪ができることがあるので、くり返す（最大5回）。
- **切った辺の記憶**：「この文の決定は、あの文の決定を理由にしない」を、**切られた側の決定の文**を鍵にしてキャッシュに保存する。次の実行では、最初から候補から外す。両端の文が同じ限り有効。
  - 理由：記憶が無いと、反復の道筋によって入力が変わり、毎回 AI の切り方が変わる。根拠付けのやり直しが連鎖した。また、反復の回数に依存する形（「n回目に切ったものを外す」）にすると、記憶が増えるたびに道筋が変わってやり直しになった。**最初から全部外す**形が安定した。

#### 段5 結合と検証（機械）

- 全体の ID を振る。claim は `C_<決定>_cN`、gap は `G_<決定>_gN`、step は `S_<決定>_i`。
- 強連結成分（Tarjan 法）で循環を検出する。
- 根への到達：
  - premise は rooted、gap は needs_gap。
  - step の from の最も弱いものが、その step の強さになる。
  - 複数の step のうち、最も強いものを採る。
  - **循環の中どうしの支えは数えない**。
- 自前の推論の完結：ほかの決定を rooted とみなして同じ計算をする。
- gap の効き：根に届かない各決定について、依存を推移的にたどって、到達する gap を数える。

#### 段7 反論（AI）

- 対象は**自前の推論が完結した決定だけ**。
  - 理由：gap を抱える決定は、プランが直れば根拠付けがやり直しになる。先に反論にかけるのは無駄になる。
- 入力は、その決定の祖先の部分グラフ。**ほかの決定のところで切る**。ほかの決定は別のジョブで審査されるので、前提として扱い、それ自体には反論しない。
- 観点：
  - logic：前提から本当に導けるか。別案を本当に退けているか
  - missing：プランに無い前提を暗黙に使っていないか
  - fact：前提の事実は十分か
  - value：人間の重視するもの次第で答えが変わる判断を、黙って決めていないか
- 各反論は、AI が自分で処理まで行う（refuted / accepted / needs_human）。refuted には、根拠の id（`by`）か、プランからの一字一句の引用（`by_quotes`）が必須。
- 検証（機械）：
  - target と by が部分グラフに実在すること
  - by_quotes が正規化したプラン本文に実在すること
  - **refuted の根拠が根に届くこと**。届かなければエラーにする（issue224 では2件。根拠にした決定自体が gap 待ちだった）

#### 段9 レポート（機械）

並び順は次のとおり。
1. 人間への質問（価値判断の gap。**止めている決定の数の多い順**）
2. 人間への質問（needs_human の反論）
3. AI が調べて直す（事実・要求の gap。効きの順）
4. AI がプランを直す（accepted の反論）
5. 循環論法
6. 根拠の無い決定

### 6.5 実行役（AI 側）の規則（EXECUTOR.md の全文）

```
1. ジョブファイル（JSON）を Read で読む。
2. instructions に従い、input だけを材料にして答えを作る。
   - input 以外のファイル（プラン本体、他のジョブ、他のジョブの結果）は開かない。
   - ジョブは互いに独立である。前に処理したジョブの内容を持ち込まない。
3. previous_errors が空でなければ、それは前回の結果が機械検証で落ちた理由である。必ず直す。
4. 答えの JSON だけを、out_path に Write で書く。前置きや説明文、コードフェンスは書かない。
5. スクリプトや一括生成のコードを書いて済ませてはならない。1件ずつ内容を読んで判断する。
全部終えたら、処理した件数と、判断に迷ったジョブがあればその job_id と理由を1行ずつ返す。
```

モデルの使い分け（実験時）：分類と根拠付けは安価なモデル（sonnet）。裁定・輪を断つ・反論は強いモデル（既定のモデル）。

### 6.6 キャッシュの粒度で分かったこと（重要）

「1行直したら、どれだけやり直しになるか」を測りながら直した。

| 版 | 1行の修正で AI に回った根拠付け | 原因 |
|---|---|---|
| 分類を**節単位**でキャッシュ | 34件 | 1行直すと、同じ節の13単位が分類し直しになる。言い回しが揺れて、下流がすべて変わる |
| 分類を単位ごと、鍵に**前後の文を含める** | 23件 | 直した行の前後2単位も分類し直しになり、決定の文が揺れる |
| 分類を単位ごと、**鍵は自分の本文だけ** | 12件（その後、輪の処理で数件増える） | 直した行を候補に含む決定（同じ節の9件と、追加候補で拾った3件）だけ。依存のとおりで、無駄ではない |

教訓：
- **AI の出力は揺れる**。キャッシュの鍵を広く取るほど、揺れが下流に伝わる。鍵は、意味の上で依存しているものだけにする。
- 「同じ入力なら同じ出力」をキャッシュで作ることが、**周回ごとの揺れを止める**手段にもなる。
- 決定の ID は単位の本文のハッシュから作る。だから文を直すと ID が変わり、それを候補に含む決定が自動的にやり直しになる。

## 7. 実験の結果

### 7.1 1周目（run1）：すべて AI のエージェントに任せた場合

- **やり方**：抽出役を2つ独立に動かし、決定を和集合にした。それを3分割して根拠グラフを作らせ、結合し、反論役を回した。検証は `check.py`。
- **抽出**：A は71件、B は70件。A だけにあるもの4件、B だけにあるもの1件。和集合は72件。
  - 例：B だけが「カンバンの選択肢 ID は起動時に焼き込んだまま、読み直しで取り直さない」を拾った。
  - **抽出は1回では漏れる。**

| 結果 | 件数 |
|---|---|
| 決定 | 72 |
| プランの前提だけで根に届いた | 16 |
| gap に頼っている | 40 |
| 根に届かない | 16 |

- gap の効き：1つの gap が最大30件の決定を止めていた。46件中26件の gap は1件しか止めていない。
- コスト：エージェント6つで約67万トークン、約15分（137行のプラン）。continuo_design.md（18,000行）に同じことをすると、1周で数千万トークン規模になる。

### 7.3 キャッシュの確認（run2 → run4）

- **何も変えずに再実行**：AI のジョブは0件。
- **1行だけ直して再実行**：表の reflect の行に「map の比較で足りるので新たに持ち込まない」を書き足した。
  - AI のジョブは28件（分類2、裁定1、根拠付け21、輪を断つ3、反論1）。全部やり直す132件の約2割。
  - 狙いの価値判断の gap（reflect を持ち込まない方針）は消えた。
  - 代わりに、別案ごとの細かい gap が3件出た。「`reflect.DeepEqual` では、どのキーが変わったかを報告できない」「`reflect` で構造体を走査する案は追加の負担だけ」「外部ライブラリの依存は見合わない」。
  - gap の総数は63から70に増えた。**AI が挙げる別案の数が実行ごとに揺れる**ため、1回の修正で gap が必ず減るわけではない。

### 7.4 コストについて分かったこと

- サブエージェント1回あたり、課題が1件でも**約7万トークンの固定分**がかかる（指示や環境の読み込み）。課題を多く詰めた回でも7〜13万トークン。**1回に詰める課題の数を増やすのが最も効く。**
- 根拠付けの1回目と2回目は直列になるので、往復の待ち時間が増える。

## 8. 分かったこと（設計上の結論）

> 1本のプラン（issue224）での実験から得た結論である。ほかのプランで成り立つかは、12章の試用で確かめる。

1. **AI に任せるのは意味の判断だけで足りる**。分割・候補・ID・引用・検証・順位付け・周回の制御は、すべて機械でできる。
2. **抽出は独立に2回行い、機械で比べる**。食い違いは全体の1割未満で、裁定のコストは小さい。
3. **循環は、決定ごとに独立に作業させると必ず生じ、結合して初めて見える**。全体を1つのグラフにして検査する工程と、輪を断つ段が必須。
4. **gap は2つの経路に分かれる**。
   - 事実・要求の gap → AI がコードや文書を調べてプランに書き足す。
   - 価値判断の gap → 人間への質問。**止めている決定の数で順位を付ける**と、少ない質問で多くの決定が前に進む。
5. **反論の結果も機械で検証する**。反証の根拠が gap 待ちなら認めない。
6. **キャッシュの鍵は、意味の上で依存しているものだけにする**。揺れの伝播を止める。
7. 現実のプランは、**ほとんどの決定がプランに書かれていない前提に頼っている**（50件中48件）。この仕組みの価値は、それを機械的に洗い出し、順位付きの質問と修正リストにすることにある。

- 「gap は必ずどれかの step で使う」を、根拠付けの指示文に入れる。今は呼び出すたびの依頼文で補っている。指示文を変えると版が上がり、根拠付けが全件やり直しになる。

   - issue134_136_140 は34%の行がコードブロックで、Go のコメントに決定が書かれている。例：「**永続化しない。**再起動すると消えるが、次の巡回で作り直される。」「**判定には1度も使わない。**」。型の定義（`type GateReason string` を文字列にする、など）そのものも決定である。
   - mermaid の図（30個）や、yaml・json の設定例にも決定が入りうる。
2. **1単位に決定がいくつも入る。**
   - 表の1行が1,208字（continuo_design.md）、893字（issue263）になる。1つのセルに、閉じる対象の集合の定義と、3つの場合分けが書かれている。
   - 単位を引用の最小粒度にしているので、引用が粗くなる。1単位から複数の決定を分ける規則はあるが、長い単位で漏れずに分けられるかは未確認。
3. **節が巨大だと、候補の規則が壊れる。**
   - continuo_design.md の最大の H2 節は9,259単位ある。「同じ H2 節」の規則がほぼ全体を指し、上限80件で前後の数件しか残らない。
   - 節番号（3-24、3-68 など）の階層や、リンクでの参照を使う必要がある。
4. **プランが別の文書に依存している。**
   - 33ファイル中20ファイルが continuo_design.md に言及し、5ファイルが「この文書が正である。continuo_design.md の 3-68 を、この3件の範囲で具体化したもの」と書く。
   - 根拠の前提が**別のファイル**にある。1ファイルで閉じる設計（S3）は、実際の使い方と合わない。
5. **プランの中に「人間が決めたこと」がある。**
   - issue245 などには「1. 人間が決めたこと」の表がある。何を・どう決めたか・いつ（JST の時刻）・人間の原文の引用が並ぶ。
   - これは fact / requirement / value のどれでもない、**人間の決定**という種類の前提で、根っこにできる。issue224 には無かったので、前提の種類にも入っていない。
6. **continuo の書き方の約束に依存している。**
   - 候補の規則が使う「冒頭の目標の節」は、continuo の「言いたいこと」（33ファイル中29ファイルにある）を前提にしている。
   - バッククォートの識別子を含む単位の割合も、13%〜87%とファイルによって大きく違う。
   - ほかのプロジェクトのプランには、こうした約束は無い。
7. **日本語だけを前提にしている。**文の分割は「。」だけで行う。英語のプランでは1行が1単位になる。
8. **「プラン」ではない文書が混ざる。**
   - `docs/plans/` には todo.md、pending_requests.md、release_v0113.md、never_forget_instructions.md なども置かれている。
   - どれを入力にするか、文書の種類ごとに「決定」の定義を変えるかは、決まっていない。
9. **数値はすべて1本から出したもの。**決定の密度（1単位あたり約0.5件）、候補の規則で拾える割合（79%）、A/B の食い違い（8%）は、ほかのプランでは違う可能性が高い。

### 10.3 この点検から出てくる仕様の方向（提案。未確定）

- 入力は「文書の集合」にする。プランと、それが参照する上位の設計文書の節を含める。
- 単位の種類に、コードブロック（中のコメント・型・設定値）と図を加える。長い単位は、分類の段で AI に分けさせ、その分け方を機械で検証する。
- 前提の種類に「人間の決定」を加える。プランの中の表、issue のコメント、セッションの記録のどれから来ても、同じ扱いにする（11章）。
- 候補の規則から、特定の書き方（「言いたいこと」など）への依存を外す。節番号やリンクなど、文書の構造を一般的に使う。
- 言語に依存しない分割にする。
- 評価用に、性質の違うプランを最低5本選んで固定する。短い・長い・コードが多い・人間の決定表がある・continuo 以外、の5種類。

## 11. 発言者の扱い（continuo との組み合わせ）

> オーナーの指摘（S1）：OSS にするなら continuo との組み合わせもスコープに含める。issue の本文やコメントで、誰が何を言ったかも正しく扱えるようにする必要がある。

### 11.1 なぜ要るか

- 設計の価値判断の多くは、人間が issue のコメントやチャットで答えている。それを根っこに使えないと、**人間がすでに答えた質問を、また聞くことになる**。
- 逆に、AI の発言を人間の発言として根っこにすると、根拠の無い決定がすり抜ける。この仕組みの存在意義が崩れる。

### 11.2 実データで分かっていること

- **アカウントでは区別できない。**issue #224 の本文とコメント40件は、すべて `maimuzo` アカウントの投稿だった。continuo の AI も、人間と同じアカウントで書いている。
- **continuo は本文の先頭に印を付けている。**
  - 40件中34件に `<!-- continuo:agent -->` などの印があり、AI の投稿と分かった。
  - 印の無い6件のうち3件は、「PR がコンフリクトしているので修正して」のような短い文で、明らかに人間だった。
  - 残る3件と issue 本文は、表を使った指示書の形式だった。人間が別のセッションの AI に書かせて貼った可能性があり、判定できなかった。
- **continuo には、この区別のための設計がすでにある。**`docs/plans/impl/issue245_issue_comment_author_marker.md`（issue #245、PR #254）。
  - AI が書くコメントは、本文の先頭に `<!-- continuo:… -->` の HTML コメントか、レビューの目印（`<!-- code-review-result -->` など）を置く。
  - 読むときに jq の式で `written_by`（`"ai"` か `"human"`）と `trusted_comment`（命令として扱ってよいか）を足す。
  - 人間が自分で起動した Claude Code には、plugin `continuo-issue-comments` を入れてもらい、`<!-- continuo:ai -->` を付けさせる。
  - 印は本文の**先頭**にあるものだけを数える。
  - 現在の印の種類：`continuo:agent`、`continuo:ai`、`continuo:progress`、`continuo:group`、`continuo:self`、`continuo:plan`、`continuo:closed`、`continuo:bid` など。
- **Claude Code のセッション記録（JSONL）でも区別できる。**
  - 人間の入力は `type: "user"` の行。ただし、ツールの実行結果も `type: "user"` で記録されるので、中身が `tool_result` の行は除く。
  - フックにはセッション記録のパス（`transcript_path`）が渡される。
- **プランの中の「人間が決めたこと」の表**（10.2 の5）には、人間の原文と時刻がある。
  - 原文がセッション記録や issue のコメントに実在するかを照合すれば、AI が書き写すときの改変を検出できる。

### 11.3 決めること（未確定）

| 項目 | 問い |
|---|---|
| 発言の出所 | issue 本文・issue コメント・PR コメント・レビュー・セッション JSONL・プラン内の表。どれを、どの優先順で使うか |
| 発言者の判定 | continuo の印（`written_by`）をそのまま使うか、独自に判定するか。continuo を使わない利用者の場合はどうするか |
| 判定できない発言 | 印の無い指示書形式の投稿などを、人間扱い・AI 扱い・保留（人間に確認する）のどれにするか |

## 12. 進め方：一旦実装して、実際に使ってみる

> オーナーの指摘（W2）：今は机上の空論で、どれぐらい効果があるかは未知数。一旦実装して、実際に使ってみる。

### 12.1 方針

- 6章のパイプラインを土台に、**ループが一周閉じる最小の形**を先に作る。作り込みは後にする。
- 実際の設計作業（continuo の次の issue のプランなど）で使う。効果と負担を記録する。
- 10章・11章の課題は、**使ってみて実際に困ったものから**片付ける。全部を先に設計しない。

### 12.2 最小の形に入れるもの（提案）

1. 6章のパイプライン（分割 → 分類 → 根拠付け → 輪を断つ → 反論 → レポート）。
2. **プランの修正**（AI）：レポートの「AI が調べて直す」と「AI がプランを直す」を、プランの写しに反映する。
3. **人間への質問**：価値判断の質問を、効きの順にまとめて人間に出す。回答をプランに反映する。
4. **周回**：最初から作り直して再実行する。周回ごとの数を記録する（gap、反論、質問）。
5. 10.2 のうち、使う前に直さないと結果が出ないもの。コードブロックを捨てないこと、別文書の参照、は優先度が高い。

### 12.3 測ること（提案）

| 測るもの | どう測るか | 何が分かるか |
|---|---|---|
| 指摘の当たり率 | accepted の反論と gap のうち、人間が見て「本当に直すべきだった」と判断した割合（標本を人間がラベル付けする） | 作り話や過剰な指摘がどれだけ混ざるか |

| コスト | AI のジョブ数、トークン、時間。1行の修正あたり、プラン1本あたり | 規模を広げられるか |

## 付録A 段ごとの指示文（実験時の全文）

```text
[classify]
あなたは設計プランの文を分類する。input.units の各単位（文・箇条書き・表の1行・見出し）に、次のラベルを付けよ。
- decision: プランが何かを選んでいて、要求を満たす別の選び方があり、選び方で振る舞いや作り方が変わるもの。「何を作る/作らない」「どう作る」「どの順」「何を例外にする」「何を出す/出さない」「数値・既定値」を全部含む。1単位に複数あれば分ける。text は一文で言い直した決定、alternatives は現実的な別案を1つ以上。
- premise: 決定ではない前提。ptype は fact（現状の事実）/ requirement（満たすべき要求・目標）/ value（何を重視するか）。text は一文で言い直した前提。
- 両方を含む単位には両方を付ける。どちらでもない単位は labels を空にする。迷ったら拾う側に倒す。
各単位は独立に判断してよいが、section_path と neighbors で文脈を確かめること。
出力は JSON: {"units":[{"uid":"...","labels":[{"kind":"decision","text":"...","alternatives":["..."]},{"kind":"premise","ptype":"fact","text":"..."}]}]}
input.units のすべての uid を、過不足なく1回ずつ出すこと。

[adjudicate]
設計プランの1つの単位について、2人の分類者の結果（input.A と input.B）が食い違った。基準に照らして正しいラベルを決めよ。
基準: decision = プランが選んでいて、別の選び方があり、選び方で振る舞いや作り方が変わるもの（1単位に複数あれば分ける）。premise = 決定ではない前提で、ptype は fact / requirement / value。どちらでもなければ空。迷ったら拾う側に倒す。
出力は JSON: {"labels":[{"kind":"decision","text":"...","alternatives":["..."]} | {"kind":"premise","ptype":"fact","text":"..."}]}

[link]
設計プランの1つの決定（input.target）について、それを支える理由を input.candidates の中から探し、推論の段（step）として書け。
規則:
1. input.candidates はプランの単位ごとのまとまりで、plan_text がプランの原文、nodes がその単位から取り出した決定・前提である。根拠の葉は nodes の id だけ。candidates に無いことを根拠にしてはならない。candidates の他の決定（kind=decision）も根拠に使ってよい。
2. 必要なのに candidates に無い前提は gaps に書く（ptype は fact / requirement / value）。でっち上げやこじつけは禁止。根拠が無いなら gap で示すのが正しい結果である。
3. step は小さく保ち、間に claims を挟んでよい。warrant に「なぜこの前提からこの結論が導けるか」を書く。
4. target.alternatives を退ける理由まで根拠付ける。退ける理由が無ければ gap にする。
5. candidates に無いが、プランの別の箇所に書かれていそうな前提や決定があれば、need に「探してほしい内容」を短く書く（無ければ空）。
claims と gaps の id は c1, c2, ... / g1, g2, ... とする。step の to は target.id か claims の id。
出力は JSON: {"claims":[{"id":"c1","text":"..."}],"gaps":[{"id":"g1","ptype":"fact","text":"..."}],"steps":[{"from":["..."],"to":"...","warrant":"..."}],"need":["..."]}
input.previous があれば、それは前回のあなたの結果である。追加された candidates を使って全体を書き直せ。
（実行時の依頼文で追加していた規則: input.excluded_note があれば必ず守ること。gaps に書いたものは必ずどれかの step の from に入れること。）

[decycle]
設計プランの決定どうしが、互いを理由にし合って輪（循環論法）になっている。輪は根拠にならない。
input.nodes は輪の中の決定、input.edges は「from の決定を理由にして to の決定を根拠付けた」辺で、warrants はその理由の説明である。
各辺について、from が本当に to より先に決まっている理由（前提・制約）なのか、それとも to と並列の決定や、to から導かれる帰結にすぎないのかを判断し、本当の理由ではない辺を切れ。
切った後に輪が1つも残らないようにすること（スクリプトが検査する）。切る辺はできるだけ少なくし、それぞれ理由を書く。
出力は JSON: {"cuts":[{"from":"...","to":"...","reason":"..."}]}

[review]
あなたは敵対的なレビュー担当である。input.target の決定は、input.nodes と input.steps の推論でプランの前提まで根拠がつながったとされている。本当に成り立つかを疑い、反論を出せ。甘い評価は不要。反論が無ければ空でよい。
target 以外の decision は別のジョブで審査されるので、ここでは成り立つものとして扱ってよい（それ自体への反論は出さない）。審査するのは target に至る推論である。
観点: logic（前提から結論が本当に導けるか、別案を本当に退けているか）/ missing（プランに無い前提を暗黙に使っていないか）/ fact（前提の事実が結論を支えるのに十分か）/ value（人間が重視するもの次第で答えが変わる判断を黙って決めていないか）。
各反論は自分で処理まで行う: refuted（input.nodes の premise や既存の推論で反証できる。by にその id を挙げるか、by_quotes にプラン本文からの一字一句の引用を挙げる）/ accepted（反論が正しい。プランの修正が要る）/ needs_human（人間の価値判断が要る）。
target には input.nodes の id か input.steps の id を書く。
出力は JSON: {"defeaters":[{"target":"...","type":"logic","text":"...","status":"accepted","by":[],"by_quotes":[],"note":"..."}]}
```
